# pcagent Web UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local chat page in the feel of Claude's chat, served by the existing pcagent FastAPI server. It shows the agent's tool calls inline with their policy decisions and Jev scores, and has Approve and Reject buttons.

**Architecture:**
- Three static files (`index.html`, `app.js`, `styles.css`) are served by FastAPI and call the existing threads, runs and approvals API.
- One new endpoint, `GET /threads`, lists conversations from the checkpointer for the sidebar.
- No build step.

**Tech Stack:** FastAPI StaticFiles, vanilla JS (ES modules), CSS custom properties, `marked` and `DOMPurify` pinned from cdnjs, pytest and httpx.

**Spec:** `docs/superpowers/specs/2026-11-22-web-ui-design.md`

## Global Constraints

- Local proof of concept only: no login, no hosting, no streaming, no Node or other build toolchain.
- Name and branding: the page is called **"pcagent"** and uses its own accent colour. Do not use Anthropic's logo, its name in the page title or UI, or a copied Claude asset.
- Assistant Markdown always goes through `DOMPurify.sanitize(marked.parse(text))`. Tool arguments and results are set with `textContent` only, never as HTML.
- Pin CDN scripts to exact versions, `marked@12.0.2` and `dompurify@3.1.6` from cdnjs, with the page still working (as plain text) if they fail to load.
- Keep the existing API contract unchanged. Use the existing run result shape: `status`, `messages`, `pending` and `decisions`. Decision dicts have the keys `tool_call_id`, `tool`, `arguments`, `action`, `reason`, `source` and `judgments`.
- Manual checks use the local mock only (`PCAGENT_SERVERS=servers.local.yaml`). Never call the deployed PAS.
- Commits end with:
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`
  `Claude-Session: https://claude.ai/code/session_018w8PsPDGNMHqcbFwbiaP7r`

## Review Focus

1. **Hostile tool output.** A claim note containing `<img src=x onerror=alert(1)>` must render as visible text, with no script and no dialog (Task 2: a manual check plus a grep test that no `innerHTML` takes tool data).
2. **Reloading `/?thread=<id>` while a call is pending** shows the approval card again, built from `GET /threads/{id}`'s `pending` (Task 2, manual check).
3. **Double-clicking Approve, or sending while a request is in flight.** Buttons and the message box are disabled until the response arrives, and a 409 "thread busy" shows a banner, not a crash (Task 2).
4. **An unknown or garbage `thread` in the URL** shows a "conversation not found" banner and a working "New chat" (Task 2).
5. **A `GET /threads` thread with no human message,** for example one created but never used, either has a fallback title or is left out. The sidebar never shows an empty row (Task 1).

### Task 1: The `GET /threads` endpoint and static serving

**Files:**
- Modify: `src/pcagent/runs.py`: add `list_threads`.
- Modify: `src/pcagent/api.py`: add the `GET /threads` route, mount `/static`, and serve `/`.
- Create: `src/pcagent/web/index.html`. A minimal placeholder for now; Task 2 replaces it.
- Test: `tests/test_api.py`: add tests.

**Interfaces:**
- Produces `async list_threads(graph) -> list[dict]`.
  - Each entry is `{"thread_id": str, "title": str, "updated_at": str}` (an ISO timestamp), newest first.
  - It reads `graph.checkpointer.alist(None)` and keeps the newest checkpoint per `configurable.thread_id`. It skips threads with no HumanMessage (Review Focus 5).
  - The title is the first HumanMessage's text, with whitespace collapsed and cut to 60 characters, with "…" added when cut.
- `GET /threads` returns `list_threads(...)` as a JSON list.
- `GET /` returns `src/pcagent/web/index.html` (a `FileResponse`). `/static` is a `StaticFiles` mount of `src/pcagent/web/`, with its path resolved from `__file__`.
- Existing routes are unchanged. Register `GET /threads` before `GET /threads/{thread_id}`.

### Task 2: The chat page

**Files:**
- Replace: `src/pcagent/web/index.html`.
- Create: `src/pcagent/web/app.js`, `src/pcagent/web/styles.css`, `tests/test_web_static.py`, `docs/layers/09-web-ui.md` (at most about 40 lines).
- Create (manual): `docs/img/ui-*.png` screenshots.

**Interfaces:**
- Consumes the API routes:
  - `POST /threads` returns `{thread_id}`.
  - `POST /threads/{id}/runs` with `{message}` returns the run result. A 409 has a `detail` of "awaiting approval" (with `pending`), "thread busy" or "interrupted run".
  - `POST /threads/{id}/approvals` with `{decisions: {tool_call_id: {approved, note}}}` returns the run result.
  - `GET /threads/{id}` returns `{thread_id, messages, pending, audit}`, or 404.
  - `GET /threads` returns `[{thread_id, title, updated_at}]`.
- Serialized message shape: `{type: "human" | "ai" | "tool", content, tool_calls?, tool_call_id?, status?}`.
- Tool rows join an AI message's `tool_calls[i].id` to the decision with the same `tool_call_id` (from `audit`, or the run's `decisions`). The latest record per id wins, so a `human` record overrides a `rule` record, which overrides a `jev` record. The tool's result is the `tool` message with the same `tool_call_id`.

**Page behaviour (the builder picks the exact styling):**
- **Layout:**
  - A sidebar about 260px wide with the "pcagent" wordmark, a "+ New chat" button and the `GET /threads` list (the active thread highlighted).
  - A main column with the conversation, max width 720px, centered.
  - A rounded message box pinned to the bottom. Enter sends and Shift+Enter adds a newline.
- **Themes:** a warm off-white light theme and a dark theme that follows `prefers-color-scheme`, defined as CSS variables on `:root`. Use a serif font for assistant text and sans-serif for everything else.
- **Messages:**
  - Human messages are right-aligned bubbles.
  - AI text is unboxed Markdown, sanitized.
  - Tool rows are collapsible, using `<details>`. The summary is a friendly verb, the tool name, and a chip: ALLOW green, ASK amber, DENY red, plus "· Jev" when the source is `jev` and "· you" when it is `human`. The body shows the arguments as preformatted text, the reason, the source, four score bars when `judgments` is present (intent, grounded and injected on a 0–1 scale; impact on a 0–3 scale), and the tool result as preformatted text.
- **Pending approvals:**
  - Each pending decision shows an amber card with the tool, the arguments, the reason, and Reject and Approve buttons. Approving or rejecting posts approvals for **all** pending ids at once, using the user's choice for each card. Recommended: a single "Submit decisions" step when there's more than one pending call, or immediate submit when there's exactly one.
  - Buttons and the message box are disabled while a request is in flight (Review Focus 3).
- **URL state:**
  - `/?thread=<id>` loads that thread with `GET /threads/{id}` and renders it. A 404 shows a "Conversation not found" banner (Review Focus 4).
  - A new chat creates a thread on the first send, then uses `history.replaceState` to set `?thread=`.
- **While waiting:** a "thinking…" indicator.
- **Banners:**
  - Server unreachable: "Can't reach the pcagent server".
  - 409 "thread busy": "Still working on the last message".
  - 409 "interrupted run": "This conversation was interrupted — start a new chat", with a button.
- **Safety:** tool data is set only through `textContent`. Assistant Markdown goes through DOMPurify. If marked or DOMPurify is missing, show the text with `textContent`.
